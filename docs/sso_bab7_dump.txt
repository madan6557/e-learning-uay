684: 7. Authentication & Session
685: 7.1 Login Flow
686: Proses autentikasi pada UAY SSO menggunakan Keycloak sebagai Identity Provider (IdP) dan OpenID Connect (OIDC) sebagai protokol autentikasi. Aplikasi yang terintegrasi dengan SSO tidak menangani username dan password secara langsung, tetapi mengarahkan pengguna ke Keycloak untuk melakukan proses autentikasi. Setelah autentikasi berhasil, Keycloak mengembalikan authorization code kepada aplikasi melalui redirect URI yang telah terdaftar. Aplikasi kemudian melakukan pertukaran authorization code tersebut untuk memperoleh token yang diperlukan. Dengan mekanisme tersebut, credential pengguna tetap berada dalam pengelolaan Keycloak dan tidak dikirimkan kepada aplikasi.

720: 7.2 OpenID Connect
721: OpenID Connect digunakan sebagai lapisan identity pada OAuth 2.0 untuk memungkinkan aplikasi memperoleh informasi identitas pengguna yang telah berhasil diautentikasi. Keycloak bertindak sebagai OpenID Provider yang menerbitkan token berdasarkan konfigurasi client dan hasil autentikasi pengguna. Aplikasi tidak perlu membuat mekanisme autentikasi username dan password sendiri. Identitas pengguna direpresentasikan menggunakan identifier yang diterbitkan oleh Keycloak dan dapat dipetakan ke account pada database UAY. Dengan demikian, autentikasi terpusat dan dapat digunakan oleh berbagai aplikasi dalam environment UAY.
722: Setiap aplikasi yang menggunakan SSO harus didaftarkan sebagai client pada Keycloak. Client tersebut memiliki konfigurasi seperti client_id, redirect URI, allowed origin, dan parameter OIDC lain yang diperlukan. Database UAY menyimpan client_id sebagai referensi integrasi pada entity applications, sedangkan detail credential dan konfigurasi autentikasi tetap dikelola oleh Keycloak. Aplikasi tidak diperbolehkan menggunakan credential client milik aplikasi lain.
723: 7.3 Authorization Code + PKCE
724: Aplikasi frontend menggunakan Authorization Code Flow dengan Proof Key for Code Exchange (PKCE). PKCE digunakan untuk mengurangi risiko penyalahgunaan authorization code selama proses autentikasi, terutama pada aplikasi yang berjalan pada browser. Frontend membuat code_verifier dan code_challenge sebelum mengarahkan pengguna ke Keycloak. Setelah pengguna berhasil melakukan autentikasi, Keycloak mengembalikan authorization code ke callback aplikasi. Aplikasi kemudian menggunakan authorization code dan code_verifier untuk memperoleh token dari Keycloak.

Implementasi frontend menggunakan OIDC client library untuk menangani state autentikasi, callback, token, dan logout sesuai konfigurasi SSO.
751: 7.4 Access Token
752: Access Token merupakan credential yang digunakan untuk memberikan akses kepada resource yang dilindungi. Dalam arsitektur UAY, Access Token diterbitkan oleh Keycloak dan digunakan oleh aplikasi atau backend aplikasi ketika mengakses resource yang membutuhkan autentikasi. Backend tidak boleh hanya mempercayai keberadaan token, tetapi harus melakukan validasi terhadap token sebelum memberikan akses. Validasi sekurang-kurangnya mencakup signature, issuer, audience, expiration, dan klaim lain yang relevan dengan client aplikasi. Token tidak boleh dicatat ke dalam audit log, application log, maupun database UAY.
753: Untuk komunikasi dengan backend API, token dikirim menggunakan mekanisme HTTP Authorization Bearer. Backend kemudian menentukan identity pengguna berdasarkan token yang telah tervalidasi. Identity tersebut dipetakan dengan account UAY melalui keycloak_user_id dan selanjutnya dapat dikaitkan dengan users.user_id.
754: Contoh konsep request:
755: Authorization: Bearer <access_token>
756: Nilai token pada contoh tersebut hanya digunakan sebagai ilustrasi dan tidak boleh disimpan atau ditampilkan dalam bentuk plaintext pada log.
757: 7.5 Identity Claims
758: Token dan endpoint identity yang disediakan oleh Keycloak dapat membawa informasi identitas pengguna yang diperlukan oleh aplikasi. Informasi tersebut harus dibatasi pada data yang memang diperlukan dan tidak digunakan sebagai pengganti database domain aplikasi. Identifier utama untuk pemetaan identity adalah sub, yang merepresentasikan subject identifier dari Keycloak. Aplikasi dapat menggunakan claim standar seperti preferred_username dan name untuk kebutuhan tampilan, sedangkan status dan data domain lainnya tetap mengikuti sumber data yang telah ditentukan.

Claim tambahan hanya ditambahkan apabila terdapat kebutuhan teknis atau bisnis yang jelas. Password, credential, refresh token, client secret, dan data sensitif lainnya tidak menjadi bagian dari identity information yang diberikan kepada aplikasi.
768: 7.6 Application Integration
769: Setiap aplikasi yang membutuhkan SSO harus terdaftar sebagai application pada database UAY dan sebagai client pada Keycloak. Entity applications menyimpan informasi integrasi seperti nama aplikasi, client_id, dan status aplikasi. Keycloak menggunakan client tersebut untuk mengenali aplikasi yang meminta autentikasi, sedangkan SSO menggunakan metadata aplikasi untuk menentukan application access dan konteks authorization pengguna. Aplikasi yang berstatus DISABLED tidak boleh digunakan untuk memperoleh akses melalui SSO. Pengelolaan registrasi, perubahan, dan penonaktifan aplikasi dilakukan oleh Super Admin.

828: 7.8 Role & Authorization Context
829: Setelah application access dinyatakan aktif, sistem menentukan role yang terkait dengan access tersebut melalui application_access.role_id. Role tersebut harus berasal dari application yang sama dengan application yang sedang diakses. Sebagai contoh, user dapat memiliki role DOSEN pada E-Learning dan role ADMIN pada File Service tanpa menjadikan kedua role tersebut sebagai role global. Dengan model tersebut, role selalu mempunyai konteks application dan tidak boleh diperlakukan sebagai hak akses universal. Validasi hubungan antara application, role, dan application access harus ditegakkan pada backend dan database sesuai kemampuan constraint yang digunakan.

Setelah token Keycloak tervalidasi, backend aplikasi dapat meminta authorization context kepada SSO Backend menggunakan identity dari token dan konteks application yang sedang digunakan. 861: 7.10 Refresh Token
862: Refresh Token digunakan untuk memperoleh Access Token baru setelah Access Token sebelumnya mendekati atau mencapai masa berlaku. Pengelolaan refresh token dilakukan oleh Keycloak dan tidak menjadi data yang disimpan dalam database aplikasi UAY. Aplikasi harus mengikuti konfigurasi lifecycle token yang ditetapkan pada Keycloak. Refresh token tidak boleh dicatat pada log dan tidak boleh dikirimkan ke service yang tidak membutuhkan fungsi refresh. Apabila session Keycloak telah berakhir atau refresh token tidak lagi valid, pengguna harus melakukan autentikasi kembali.
863: 7.11 Session Lifetime
864: Session SSO dikelola oleh Keycloak dan tidak direplikasi sebagai session authentication table pada PostgreSQL UAY. Lifecycle session mencakup batas waktu idle, batas waktu maksimum, token lifetime, dan kondisi logout sesuai konfigurasi Keycloak. Nilai konkret lifetime ditentukan pada konfigurasi deployment setelah mempertimbangkan kebutuhan keamanan dan usability UAY. Aplikasi tidak boleh menganggap session yang tersimpan di browser sebagai bukti autentikasi yang berdiri sendiri. Setiap request ke resource yang dilindungi harus tetap memiliki mekanisme validasi authentication dan authorization yang sesuai.
865: 7.12 Logout
866: Logout dilakukan melalui mekanisme logout OIDC/Keycloak sehingga session authentication pada Keycloak dapat dihentikan. Setelah logout, aplikasi harus membersihkan state autentikasi lokal yang digunakan pada browser dan tidak mempertahankan access token yang masih dapat digunakan. Logout normal hanya ditujukan untuk mengakhiri session pengguna pada perangkat atau konteks aplikasi yang sedang digunakan. Aplikasi tidak boleh menganggap logout dari satu aplikasi sebagai penghapusan seluruh account pengguna pada SSO.

882: 7.13 Logout All Sessions
883: Logout all sessions digunakan untuk mengakhiri seluruh session aktif pengguna yang dikelola oleh SSO. Setelah seluruh session dihentikan, token yang bergantung pada session yang telah berakhir tidak boleh digunakan untuk memperoleh akses baru. Implementasi detail penghentian session mengikuti kemampuan dan konfigurasi Keycloak yang digunakan pada deployment UAY.
884: 7.14 Token Expiration
885: Access Token memiliki masa berlaku dan tidak boleh digunakan setelah exp terlewati. Backend harus menolak token yang telah expired meskipun token tersebut sebelumnya valid. Ketika token expired, aplikasi dapat menggunakan mekanisme refresh yang tersedia atau mengarahkan pengguna untuk melakukan autentikasi kembali apabila refresh session juga telah berakhir. Expiration token tidak menggantikan pemeriksaan application access karena status akses merupakan authorization concern. Dengan demikian, token yang masih valid secara kriptografis tetap tidak boleh digunakan untuk aplikasi apabila application access pengguna telah dicabut.
886: 7.15 Account Disablement
887: Account yang berstatus DISABLED tidak boleh digunakan untuk memperoleh akses ke aplikasi UAY. Perubahan status account harus menyebabkan akses pengguna dihentikan sesuai mekanisme session dan token yang diterapkan pada Keycloak serta authorization layer UAY. Backend aplikasi tetap harus mempertimbangkan status authorization ketika memproses request yang dilindungi. Hal ini diperlukan agar perubahan status account tidak hanya terlihat pada administrative UI tetapi benar-benar mempengaruhi akses ke resource.

Identifier tersebut kemudian disimpan pada accounts.keycloak_user_id untuk menghubungkan account UAY dengan identity Keycloak. Username dibuat berdasarkan aturan identitas yang telah ditetapkan, sedangkan username tidak dianggap sebagai alamat email institusi. 925: 8.2 Update User
926: Data user dapat diperbarui oleh user sendiri untuk field yang diperbolehkan dan oleh administrator untuk field yang berada dalam kewenangan administratif. Perubahan data harus dilakukan melalui SSO Web Application atau API resmi agar validasi, authorization, dan audit dapat diterapkan secara konsisten. Tidak semua field user dapat diubah secara bebas karena beberapa data merupakan identitas institusional yang harus mengikuti sumber data resmi. Setiap perubahan data penting harus menghasilkan audit event yang mencatat actor, target, waktu, dan perubahan yang dilakukan.

Perubahan identifier seperti NIM, NIP, atau NIDN tidak diperlakukan sebagai perubahan profile biasa apabila identifier tersebut merupakan bagian dari identitas resmi institusi. Perubahan tersebut harus mengikuti prosedur administratif yang ditetapkan dan tetap mempertahankan history identifier apabila diperlukan untuk kebutuhan audit dan integritas data.

Mengaktifkan account tidak secara otomatis memberikan seluruh application access apabila access tersebut memang telah dinonaktifkan atau telah berakhir. Setelah account aktif, pengguna dapat melakukan autentikasi kembali apabila seluruh kondisi authorization telah terpenuhi.

941: 8.4 Disable User
942: Disable digunakan untuk menghentikan kemampuan user atau account dalam melakukan autentikasi dan memperoleh akses. Administrator hanya dapat melakukan disable terhadap user yang berada dalam scope kewenangannya. Setelah disable dilakukan, authentication dan authorization terhadap user tersebut harus ditolak. Session aktif yang berkaitan dengan account juga harus dihentikan atau dibuat tidak dapat digunakan kembali sesuai mekanisme session dan token yang diterapkan.
943: Disable tidak menghapus data user dari database. Data tetap dipertahankan agar history, audit, identifier, application access, dan relasi administratif tetap dapat ditelusuri. Jika user diaktifkan kembali pada masa mendatang, data historis tidak perlu dibuat ulang selama masih valid.
944: 8.5 User Status
945: Status user digunakan untuk merepresentasikan lifecycle atau kelayakan user pada environment SSO. Status user dan status account merupakan dua konsep yang berbeda. users.status menggambarkan kondisi user pada domain SSO, sedangkan accounts.status menggambarkan apakah account authentication dapat digunakan. Pemisahan ini memungkinkan kondisi lifecycle user dikelola tanpa menjadikan account sebagai satu-satunya sumber informasi.
